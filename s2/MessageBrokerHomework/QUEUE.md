# Отчет по лабораторной работе: Брокер очередей на базе PostgreSQL

## 1. Проектирование схемы БД (Предметная область: Таможенная служба)
Для хранения очереди проверок граждан на КПП (в стиле "Papers, Please") создана таблица `tasks`.
Чтобы воркеры мгновенно находили новые задачи и база данных не тормозила из-за старых выполненных строк, реализован **частичный индекс** (Partial Index):

```sql
CREATE INDEX idx_tasks_ready_process 
ON tasks (priority DESC, scheduled_at ASC) 
WHERE status = 'Ready';
```

## 2. Реализация Продюсера и Консьюмеров
* **Продюсер (1 сервис)**: В цикле генерирует события досмотра (Проверка паспорта, сканирование биометрии, визы) с высокой интенсивностью (~200-300 задач/сек). Вставка происходит в рамках одной транзакции вместе с фиктивной записью системного аудита.
* **Приоритеты**: Реализовано распределение веса 80/20. Обычные проверки получают `Priority 0`, а критические сигналы (Поиск по базе преступников) — `Priority 100`.
* **Консьюмеры (2 сервиса)**: Запущены два независимых конкурирующих воркера (`Worker_1` и `Worker_2`).

## 3. Механизм параллельной обработки (Пессимистическая блокировка)
Для атомарной обработки без конфликтов и дублирования используется конструкция:
```sql
SELECT id FROM tasks 
WHERE status = 'Ready' AND scheduled_at <= now()
ORDER BY priority DESC, scheduled_at ASC
LIMIT 1
FOR UPDATE SKIP LOCKED
```
* `FOR UPDATE` накладывает пессимистичную блокировку на строку, чтобы другие воркеры её не изменили.
* `SKIP LOCKED` заставляет другие процессы пропускать заблокированные строки и сразу переходить к следующим, обеспечивая высокую параллельную скорость.

## 4. Нагрузка и мониторинг Лага (Результаты теста)

Контейнеры были запущены под высокой нагрузкой. Из логов терминала зафиксированы следующие показатели совместной работы:

* **Средняя пропускная способность одного воркера**: ~61-62 задач/сек.
* **Суммарный Throughput системы**: ~122-124 задач/сек.
* **Мониторинг лага очереди (разница `now() - MIN(created_at)` для статуса Ready)**:
    * Старт теста: **4.21 сек.**
    * Через 15 секунд: **13.15 сек.**
    * Через 30 секунд: **22.79 сек.**
    * Через 50 секунд: **38.86 сек.**

*Вывод теста*: Наблюдается линейный рост лага очереди. Это наглядно демонстрирует, что интенсивность генерации задач продюсером превышает максимальную пропускную способность двух консьюмеров. При этом критические задачи (`Priority 100`) обрабатываются вне очереди благодаря сортировке индекса.

## 5. Дополнительные баллы
1. **Механизм Retry (Exponential Backoff)**: Реализована симуляция ошибок (5% от всех проверок). При сбое воркер увеличивает счетчик `attempts`. Если лимит не исчерпан, задача возвращается в статус `Ready`, а время её следующей обработки `scheduled_at` сдвигается в будущее (`now() + INTERVAL '10 seconds'`). При превышении лимита задача маркируется как `Failed` (аналог Dead Letter Queue).
